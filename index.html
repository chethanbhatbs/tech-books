F1AI, machine learning and deep learning

AI is the broad goal: machines that produce predictions, recommendations, decisions or content. Machine learning (ML) is the main way to get there today: instead of hand-writing rules, you train a model on examples. Deep learning is ML with neural networks of many layers, which learn their own features from raw data.

How it works

Classic AI could be hand-written rules: "if the email contains these words, mark it spam". ML replaces the rules with a model whose internal numbers (parameters) are learned from labelled examples. Deep learning stacks many layers, so early layers learn simple patterns and later layers combine them into complex ones (LeCun, Bengio and Hinton, Nature 2015). Large language models (LLMs) are deep learning models trained on text.

Key terms

ModelTrained software that maps inputs to outputs
FeatureOne input variable, such as an email's sender
LabelThe correct answer for a training example
ParameterA number inside the model learned during training
Generative AIModels that create new content (text, images, audio) from a prompt
AI system (NIST)"An engineered or machine-based system that can… generate outputs such as predictions, recommendations, or decisions"
Where it is used
  • Spam filtering and fraud detection
  • Recommendations in shops and streaming apps
  • Chat assistants, coding assistants, image generation
Current state
  • Generative LLMs from labs such as Anthropic, OpenAI and Google lead current AI products (see the Landscape chapter).
  • NIST's AI Risk Management Framework 1.0 (Jan 2023) gives the definitions many organisations use.
Limitations
  • A model is only as good as its training data.
  • Deep learning needs large amounts of data and compute.
  • "AI" is used loosely in marketing; ask what is actually inside.
What's next
  • Whether multi-step AI agents fit existing definitions of an "AI system" is still being worked out by regulators. Open question.

QA perspective

  • Ask which kind of "AI" is inside: rules, classic ML or an LLM. Each fails differently.
  • Rules fail predictably; learned models fail on inputs unlike their training data. Test unusual inputs, not only typical ones.
  • Use the NIST AI RMF vocabulary in risk reviews and sign-offs.
Further learning

  • LeCun, Bengio, Hinton: Deep learning (Nature 2015)

F2Neural networks and how models learn

A neural network is layers of simple units ("neurons"), each computing a weighted sum of its inputs. Training adjusts the weights, step by step, until the network's outputs are close to the correct answers.

How it works

Google's ML course describes the loop as: calculate the loss, determine the direction that reduces it, "move weights and bias by a small amount", and "repeat until the model converges". Backpropagation uses the chain rule to work out how much each weight contributed to the error, which "makes gradient descent feasible for multi-layer neural networks".

Key terms

Weight and biasThe numbers the network learns
ActivationA non-linear function such as ReLU applied after the weighted sum
LossA score of how wrong the output is
Gradient descentRepeatedly nudging weights in the direction that lowers the loss
BackpropagationWorking backwards through the layers to get each weight's share of the error
Learning rateHow big each nudge is
Epoch / batchOne full pass over the training data / one slice of it
ConvergenceMore training no longer lowers the loss
Where it is used
  • Image classifiers
  • Speech recognition
  • Every modern LLM
Current state
  • Backpropagation with gradient descent is still the standard way to train neural networks (Google ML Crash Course).
Limitations
  • Vanishing gradients: early layers "train very slowly, or not at all".
  • Exploding gradients: steps grow "too large to converge".
  • Dead ReLU units get stuck outputting zero.
What's next
  • Cheaper training methods. Open.
  • Interpretability: what individual neurons and circuits represent (see Part 4). Open.

QA perspective

  • Plot training and validation loss together. When they split apart, the model is overfitting.
  • Watch for the loss turning into NaN or jumping, a sign of unstable training.
  • Fix random seeds when you need repeatable runs.
  • Test tiny input changes: a robust model should not flip its answer.

F3Supervised, unsupervised, self-supervised and reinforcement learning

Four ways a model can learn, depending on what feedback it gets: correct answers, no answers, answers hidden in the data itself, or rewards for actions.

Self-supervisedLabels taken from the data itself, such as hiding the next word and predicting itLLM pre-training
Reinforcement (RL)"Rewards or penalties based on actions performed within an environment"Game-playing agents; tuning chat models with human feedback

Key terms

ClusteringGrouping similar items without labels
Agent (RL)The learner that takes actions
EnvironmentWhat the agent acts in
RewardThe score for an action
PolicyThe agent's learned strategy
Where it is used
  • Supervised: spam and fraud classifiers
  • Self-supervised: pre-training every LLM
  • RL: aligning chat models (InstructGPT, 2022)
Current state
  • Modern LLMs combine all three: self-supervised pre-training, supervised fine-tuning, then reinforcement learning (InstructGPT, Ouyang et al. 2022).

  • Clusters found without labels may not mean anything useful.
  • An RL agent can "game" a badly designed reward.
What's next
  • Reinforcement learning on automatically checkable rewards, such as code that passes tests. Active area; no settled results to cite here.

QA perspective

  • Supervised: check label quality and whether every class has enough examples.
  • Unsupervised: have a domain expert sanity-check the groups.
  • RL: look for reward hacking, where the score rises but the behaviour is wrong.
  • For each, write down what "correct" means before testing.

F4Training, validation, inference and fine-tuning

A model is built in stages: it learns from training data, settings are tuned on validation data, it is judged once on unseen test data, and then it is used for real (inference). Fine-tuning takes a trained model and trains it a little more for a specific task.

How it works

Google's course suggests a typical 70/15/15 split and warns that training and test data must come from the same distribution. LoRA (Hu et al., 2021) is a popular cheap way to fine-tune: it freezes the original weights and trains small added matrices. The paper reports cutting trainable parameters "by 10,000 times" and GPU memory "by 3 times" compared with fully fine-tuning GPT-3 175B, with equal or better quality.

Key terms

Training setWhat the model learns from
Validation setUsed to choose settings and compare versions
Test setKept unseen until the final check
InferenceUsing the trained model to make predictions
Fine-tuningExtra training on task-specific data
LoRALow-rank adapters: fine-tune by training small added matrices
HyperparameterA setting chosen by people, such as the learning rate
Data leakageTest data that slipped into training, inflating scores
Where it is used
  • Fine-tuning an LLM on a company's support tickets
  • Choosing between model versions on a validation set
  • Serving predictions in an app (inference)
Current state
  • LoRA and related adapter methods are widely used for fine-tuning open-weight models (Hu et al. 2021).
Limitations
  • Leakage makes a model look better than it is.
  • Real-world data drifts away from the training data over time.
  • Fine-tuning for one task can weaken others.
What's next
  • Cheaper ways to adapt models. Open.

QA perspective

  • Check that training, validation and test sets do not overlap (deduplicate).
  • After fine-tuning, re-run the old tasks too, to catch regressions.
  • Test inference settings (temperature, maximum tokens) as part of the product.
  • Record the exact model version behind every result.
Further learning
  • LoRA paper (Hu et al. 2021)
  • Google: Datasets and overfitting

F5Accuracy, overfitting and model limits

How to tell whether a model is good: count what it gets right and wrong, choose the measure that matches the cost of each mistake, and check it works on data it has never seen.

How it works

For a yes/no classifier, every prediction lands in one of four boxes:

Actually yesActually no
Predicted yesTrue positive (TP)False positive (FP)
Predicted noFalse negative (FN)True negative (TN)
MetricFormulaAsks
Accuracy(TP+TN) / allHow often is it right overall?
PrecisionTP / (TP+FP)When it says yes, how often is it right?
RecallTP / (TP+FN)Of the real yeses, how many did it find?
F12TP / (2TP+FP+FN)A balance of precision and recall

Overfitting means the model "matches (memorizes) the training set so closely" that it fails on new data. Underfitting means it is poor even on training data. Regularisation methods such as L2 and dropout reduce overfitting.

Key terms

Confusion matrixThe four-box table above
PrecisionFew false alarms
RecallFew misses
OverfittingGreat on training data, poor on new data
UnderfittingPoor everywhere
DropoutRandomly switching off units during training to prevent memorising
Where it is used
  • Fraud alerts usually favour recall (miss nothing)
  • Spam filters favour precision (do not bin real mail)
  • Medical screening needs both
Current state
  • These remain the standard measures for classifiers (Google ML Crash Course).
Limitations
  • With a 1% positive class, a model that always says "no" scores 99% accuracy "despite being useless".
  • One threshold hides the trade-off between precision and recall.
  • These measures do not fit open-ended text from LLMs; see the evals topic.
What's next
  • Better ways to score generated text. See the evals topic. Open.

QA perspective

  • Always ask for the confusion matrix and the class balance, not just accuracy.
  • Choose the metric from the cost of each mistake type.
  • Compare training and validation scores to spot overfitting.
  • Score slices separately (per region, language, device): an average can hide a group that fails.

F6Tokens, embeddings and context windows

An LLM reads text as tokens (words or pieces of words), turns each into an embedding (a list of numbers), and predicts the next token, one at a time. Everything it can see in one call is its context window.

How it works

Most tokenizers use byte pair encoding (Sennrich et al., 2016): frequent words become one token, rare words several. Google's Gemini docs put a token at about 4 characters, and 100 tokens at about 60 to 80 English words. The model then generates by repeatedly predicting the next token:

# choosing the next token: temperature, then top-p (Holtzman et al. 2019)
probs = softmax(logits / T)                    # T < 1 sharper, T > 1 flatter
idx = argsort(probs)[::-1]
cum = cumsum(probs[idx])
keep = idx[: searchsorted(cum, p) + 1]         # smallest set with total >= p
next_token = sample(keep, probs[keep] / probs[keep].sum())

Anthropic defines the context window as "all the text a language model can reference when generating a response, including the response itself": system prompt, messages, tool definitions, tool results and output all count.

Key terms

TokenA piece of text the model reads or writes
TokenizerSplits text into tokens and maps them to IDs
EmbeddingA vector representing a token's meaning
Context windowThe maximum tokens visible in one call
max_tokensThe cap on output length
Temperature / top-pSettings for how adventurous token choice is
Context rotAnthropic: "accuracy and recall degrade" as the context grows
Prompt cachingReusing a processed prompt prefix to save cost and time
Where it is used
  • Chat assistants
  • Questions over long documents
  • Embeddings for semantic search (Part 2)
Current state
  • Current Claude models (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5) have a 1M-token context window and up to 128K output tokens (Anthropic docs, Oct 2026). Older models such as Sonnet 4.5 have 200K.
  • Liu et al. (2023): models do best when key information is at the start or end of a long context, worse in the middle.
Limitations
  • Context rot: more text is not always better.
  • The same text gives different token counts on different tokenizers, so costs differ.
  • Long contexts cost more and respond more slowly.
What's next
  • Compaction and context editing that summarise or clear old turns for long agent sessions (Anthropic, beta in 2026).
  • Whether bigger windows remove context rot. Open.

QA perspective

  • Test inputs near the limit. On Anthropic's API an over-long prompt returns a 400 error; output that hits the window stops with stop_reason: "model_context_window_exceeded".
  • Plant a fact at the start, middle and end of a long input and check the model finds each.
  • Read token counts from the API's usage field instead of estimating.
  • Test non-English text and emoji, which can use many more tokens.
Further learning

  • Google: LLMs and transformers
  • Lost in the Middle (Liu et al. 2023)

F7Transformers and attention

The transformer (Vaswani et al., 2017) is the architecture behind every major LLM. Its key step, attention, lets each token look at all the others and decide which ones matter for it.

How it works

Google's course frames attention as asking "how much does each other token of input affect the interpretation of this token?". Because attention processes all tokens at once instead of one by one, transformers trained much faster than the recurrent networks before them. LLMs use the decoder half, with a mask so each token only sees earlier tokens.

# scaled dot-product attention (Vaswani et al. 2017)
Attention(Q, K, V) = softmax(Q Kᵀ / √d_k) V

Q (query) is what a token is looking for, K (key) what each token offers, V (value) what it passes on. The KV cache stores past tokens' keys and values so each new token only computes its own, which speeds up generation but uses a lot of memory on long contexts.

Key terms

AttentionEach token weighs every other token
Multi-head attentionSeveral attentions in parallel, each tracking a different relationship
Encoder / decoderReads input / generates output; LLMs are decoder-only
Causal maskStops a token seeing later tokens
Positional encodingTells the model word order; RoPE is the common modern method
KV cacheStored keys and values that make generation faster
Where it is used
  • Machine translation (the original task)
  • Chat and coding assistants
  • Vision (vision transformers) and speech models
Current state
  • The 2017 paper reported 28.4 BLEU on English-German translation, a new best, after 3.5 days of training on 8 GPUs for its English-French model.
  • Transformers underpin today's LLMs (Google ML Crash Course).
Limitations
  • Attention cost grows quickly with input length.
  • Attention weights are not a full explanation of why the model answered.
  • Large transformers need a lot of compute and memory.
What's next
  • More efficient attention and alternative architectures such as state space models (Part 4). Open.

QA perspective

  • Latency and cost rise with input length: load-test with realistic long inputs.
  • Check sensitivity to word order and phrasing.
  • Do not treat attention visualisations as proof of the model's reasoning.
Further learning
  • Attention Is All You Need (2017)
  • Google: Transformers

F8Pre-training, post-training and inference

An LLM is made in two phases. Pre-training teaches it language and knowledge by predicting the next token over huge amounts of text. Post-training turns that raw model into a helpful assistant that follows instructions and refuses harmful requests.

How it works

MethodHowSource
SFTFine-tune on example conversations written by peopleInstructGPT 2022
RLHFPeople rank answers; a reward model learns their preferences; the model is optimised against itInstructGPT 2022
DPOLearns from preference pairs "with only a simple classification loss", no reward modelRafailov et al. 2023

Scaling laws: Kaplan et al. (2020) found loss falls predictably as models, data and compute grow; Chinchilla (2022) showed model size and training tokens "should be scaled equally".

Key terms

Pre-trainingNext-token prediction on a huge text corpus
Base modelThe raw pre-trained model
SFTSupervised fine-tuning on demonstrations
Reward modelA model that scores answers the way people would
RLHF / DPO / RLAIFThree ways to tune toward preferred answers
InferenceRunning the finished model
Where it is used
  • Chat assistants
  • Safety and harmlessness training
  • Tuning open-weight models for a product
Current state
  • InstructGPT: people preferred outputs from a 1.3B-parameter tuned model over the 175B GPT-3.
  • DPO matched or beat RLHF in its own experiments (2023). Each lab's current recipe is not public.
Limitations
  • Human preference labels are costly and inconsistent.
  • Models can over-optimise the reward and drift into odd behaviour.
  • Kalai et al. (2025) argue training and grading reward guessing over saying "I don't know".
What's next
  • AI feedback at larger scale. Open.
  • Whether simpler methods like DPO replace RLHF. Open.

QA perspective

  • After any model update, re-run refusal, safety and instruction-following tests.
  • Watch for sycophancy (agreeing with the user when wrong) and over-refusal.
  • Test determinism at your chosen temperature.
  • Pin model IDs; behaviour shifts between versions.

F9Prompt engineering and system instructions

Writing the input so the model does what you need: clear instructions, the right context, examples, and a defined output shape. The system prompt (called the developer message in OpenAI's API) sets standing rules above the user's messages.

How it works

Anthropic's advice starts before the prompt: define "clear success criteria" and "ways to empirically test" against them. Its "golden rule": if a colleague with little context would be confused by the prompt, so will the model.

Be clear and directSay exactly what you want and what to avoid
Examples (few-shot)Anthropic: 3 to 5 examples in <example> tags; OpenAI: cover "a diverse range of possible inputs"
StructureSeparate parts with XML tags or Markdown: <instructions>, <context>, <input>
RoleSet a role in the system prompt
Long documentsPut them at the top, the question at the end
Reasoning modelsOpenAI: give them "high-level guidance" rather than step-by-step instructions
# a structured prompt

Reply with the label only.
</instructions>
<example>Ticket: I was charged twice. Label: billing</example>
<ticket>{{ticket_text}}</ticket>

Few-shotGiving worked examples in the prompt
XML tagsLabels that separate parts of a prompt

Structured outputsForcing the reply into a JSON schema
Context engineeringChoosing everything that goes into the window, not only the instruction
Where it is used
  • Classifying text into fixed labels
  • Extracting fields into JSON
  • Writing instructions for agents
Current state
  • Anthropic notes that on Claude 4.6 and later, prefilling the start of the assistant's reply returns a 400 error; use structured outputs or tools with fixed labels instead (Oct 2026).
Limitations
  • Prompts are model-specific; a prompt tuned for one model may degrade on another.
  • Some problems (latency, cost, missing knowledge) need a different model or RAG, not a better prompt.
  • Prompts can be overridden by injected text (Part 4).
What's next
  • "Context engineering" for agents: managing everything in the window across long sessions (Anthropic).

QA perspective

  • Treat prompts as code: version them, review changes, and keep a regression test set.
  • Test that system rules win over conflicting user requests.
  • Test prompt injection through documents and tool results, not only typed input.
  • Validate every output against its expected format, and re-test on each model upgrade.

F10Hallucinations, evaluations and benchmarks

A hallucination is a "plausible yet incorrect" statement (Kalai et al. 2025). An evaluation (eval) measures how often a model gets things right on a test set. A benchmark is a public eval used to compare models.

How it works

Kalai et al. (OpenAI, 2025) argue hallucinations "originate simply as errors in binary classification" during pre-training and persist because "guessing when uncertain improves test performance": most benchmarks score "I don't know" the same as a wrong answer. Their proposed fix is to change how benchmarks are scored.

BenchmarkWhat it isStatus

GPQA448 expert science questions; PhD experts scored 65% at launchStill cited
SWE-bench2,294 real GitHub issues from 12 Python projectsOpenAI stopped reporting the "Verified" subset in Feb 2026, citing contamination reported
Humanity's Last Exam2,500 very hard questions from expertsBuilt to resist saturation

Key terms

Hallucination / confabulationFluent, confident, false output
CalibrationConfidence that matches actual accuracy

ContaminationBenchmark questions leaked into training data
SaturationTop models all near 100%, so the benchmark no longer separates them
LLM-as-judgeAnother model grading outputs against a rubric
Where it is used
  • Choosing a model for a product
  • Release gates: a new version must not score worse
  • Tracking progress across the field
Current state
  • MMLU is saturated; harder benchmarks such as Humanity's Last Exam (CAIS and Scale AI) were built to replace it.
  • Contamination is a recognised problem across public benchmarks (survey, 2024).
Limitations
  • Public scores can be inflated by contamination.
  • Saturated benchmarks stop telling models apart.
  • Right/wrong grading rewards guessing.
What's next
  • Confidence-aware grading in mainstream benchmarks. Open.
  • Benchmarks with private test sets that resist contamination. Open.

QA perspective

  • Do not rely on leaderboard scores. Build a private eval set from your own product's real cases.
  • Score "I don't know" separately from wrong answers; a wrong answer should cost more.
  • Check every factual claim and every cited source against the original.
  • Re-run evals on every model or prompt change; run each case several times and report the pass rate.
Further learning

M1RAG and knowledge systems

Retrieval-augmented generation (RAG) answers questions from your own documents: it first finds the relevant passages, then puts them in the prompt so the model answers from evidence instead of memory (Lewis et al., 2020).

How it works

Text is turned into embeddings: vectors where similar meanings point in similar directions. Search finds the stored vectors nearest the question. Hybrid search adds keyword (BM25) search to catch exact terms such as error codes, and a reranker re-scores the top hits. GraphRAG (Microsoft, 2024) instead builds a graph of entities and pre-summarised communities, which handles "whole corpus" questions that plain RAG struggles with.

# pgvector: store vectors in Postgres and find the 5 nearest by cosine distance
CREATE TABLE chunks (id bigserial PRIMARY KEY, body text, embedding vector(1536));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
SELECT id, body FROM chunks ORDER BY embedding <=> '[0.012, -0.088, ...]' LIMIT 5;
# reciprocal rank fusion: merge keyword and vector rankings (Cormack et al. 2009, k = 60)
def rrf(rankings, k=60):
    score = {}
    for ranking in rankings:
        for rank, doc in enumerate(ranking, start=1):
            score[doc] = score.get(doc, 0) + 1 / (k + rank)
    return sorted(score, key=score.get, reverse=True)

Key terms

ChunkA passage of a document, often a few hundred tokens
EmbeddingA vector that represents meaning
Top-kHow many chunks are retrieved
Hybrid searchKeyword plus vector search, merged
RerankerA second, more careful scoring pass on the top hits
GraphRAGRAG over a knowledge graph with pre-built summaries
Citation precision / recallIs each cited source relevant? Is every claim backed?
Where it is used
  • Support bots over help-centre articles
  • Company-wide document search
  • Legal and research Q&A that must show sources
Current state
  • Anthropic's "Contextual Retrieval" (Sept 2024) cut retrieval failures by 35% with contextual embeddings, 49% adding contextual BM25, and 67% adding reranking research.
  • Chunking guidance from Microsoft Azure AI Search: start at 512 tokens with 25% overlap.
Limitations
  • If the right chunk is not retrieved, the answer is wrong however good the model is.
  • Citations are often incomplete: the ALCE benchmark found the best models lacked full citation support about half the time on one dataset research.
  • GraphRAG costs many model calls to build its index.
What's next
  • Multi-step ("agentic") retrieval and graph-plus-vector hybrids.
  • How to judge answers about a whole collection without an AI judge. Open.

QA perspective

  • Test retrieval and generation separately: did the correct chunk reach the top-k at all?
  • Check every citation actually supports its sentence.
  • Ask questions the documents cannot answer: the system should say so, not invent.
  • Re-test after re-indexing, and with stale or conflicting documents.
Further learning
  • RAG paper (Lewis et al. 2020)
  • GraphRAG (Edge et al. 2024)
  • Anthropic: Contextual Retrieval

M3AI agents and agentic systems

A chatbot answers. An agent acts: it plans, calls tools, reads the results and decides the next step, in a loop, until the task is done. Anthropic separates workflows ("predefined code paths") from agents, where the model "dynamically directs its own process and tool usage".

How it works

Common patterns (Anthropic, "Building effective agents", Dec 2024): prompt chaining, routing, parallelisation, orchestrator-workers, and evaluator-optimizer. A multi-agent system has a lead agent hand parts of the task to sub-agents. A handoff passes the conversation to another agent; human approval pauses a run before a risky tool call.

# the tool loop with the Anthropic Python SDK
import anthropic
client = anthropic.Anthropic()
messages = [{"role": "user", "content": "Weather in Paris?"}]
while True:
    resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=1024,
                                  tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break                                    # final answer
    results = [{"type": "tool_result", "tool_use_id": b.id,
                "content": run_tool(b.name, b.input)}
               for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})

Key terms

Tool callThe model's structured request to run a function
Orchestrator-workersA lead agent splitting work among sub-agents
HandoffPassing the conversation to a specialised agent
Working vs long-term memoryThe current context vs stored notes across sessions
CheckpointSaved state so a run can resume
Approval / interruptionA pause for a person to allow or refuse an action
Compounding errorSmall mistakes growing over many steps
Where it is used
  • Coding agents
  • Deep research across many sources
  • Customer-service triage with handoffs
Current state
  • Anthropic's multi-agent research system (June 2025) beat a single agent by 90.2% on its internal research eval, but used about 15× the tokens of a chat; single agents use about 4× research.
  • OpenAI's Agents SDK supports handoffs and tools marked as needing approval, which pause the run until approved or rejected production.
Limitations
  • Token cost grows fast with autonomy and with more agents.
  • Errors compound over long runs.
  • It can be unclear which agent owns which state.
What's next
  • When multi-agent is worth its cost. Open.
  • Standard formats for agent memory. Open.

QA perspective

  • Check the end state (what changed in the system), not just the final message.

H1CPUs, GPUs, TPUs, NPUs and AI accelerators

Different chips trade generality for speed. A CPU handles general, branchy work. A GPU runs huge numbers of math operations in parallel. A TPU or other custom accelerator is built for the matrix math of neural networks. An NPU is a low-power AI block inside a phone or laptop chip.

How it works

Neural networks are mostly matrix multiplications. GPUs and TPUs have dedicated matrix units and work in low-precision number formats (BF16, FP8, FP4) to do more per second. Real speed depends on three things together: compute (FLOPS), memory bandwidth, and the links between chips.

Key terms

FLOPS / TOPSFloating-point / integer operations per second
FP8, FP4Low-precision number formats that trade accuracy for speed
HBMHigh-bandwidth memory stacked next to the chip
ASICA custom chip built for one job
Rack-scaleA whole rack of chips acting as one system
TDPHow much power a chip draws
Where it is used
  • Training frontier models on GPU or TPU clusters
  • Serving models in the cloud
  • On-device features such as transcription (NPU)
Current state
  • NVIDIA GB300 NVL72: 72 GPUs per rack, 288 GB HBM3e per GPU, liquid-cooled production. Vera Rubin, with HBM4, announced for 2026 claim.
  • AMD MI355X: 288 GB HBM3e, 8 TB/s production. Google TPU7x Ironwood: pods of up to 9,216 chips production. AWS Trainium3 UltraServers: up to 144 chips (Dec 2025) production.
  • Laptop NPUs reach 80 TOPS (Qualcomm Snapdragon X2 Elite) claim.
Limitations
  • Headline FLOPS use the lowest precision and are rarely reached in practice.
  • Software lock-in: CUDA, ROCm, XLA and Neuron are not interchangeable.
  • Power and cooling limit how many can be run.
What's next

  • Whether custom chips (TPU, Trainium) take share from GPUs. Open.

  • Low-precision maths changes results slightly: compare against a reference with agreed tolerances.

H2Training vs inference hardware

Training learns the weights and needs huge clusters with fast links. Inference uses the finished weights to answer requests, where cost per token and response time matter most.

How it works

Training stores gradients and optimiser state as well as weights (the Adam optimiser keeps two extra values per parameter), so it needs several times the memory, plus fast links between thousands of chips. Inference has two phases: prefill (reading the prompt, compute-heavy) and decode (writing tokens one by one, memory-heavy).

X10Human oversight and high-risk AI

For high-risk systems, the EU AI Act (Article 14) requires that people can oversee the system effectively while it is in use, and step in.

How it works

Article 14 says the people overseeing must be able to: understand what the system can and cannot do; stay aware of automation bias (over-trusting the machine); interpret its output correctly; disregard, override or reverse an output; and stop the system with a "stop" button or similar that brings it to a safe state. Remote biometric identification needs separate checks by at least two people.

X12AI research frontiers

The ideas driving the next models: scaling laws, spending more compute at answer time, mixture of experts, and new architectures beyond the transformer.

How it works

Scaling laws (Kaplan et al. 2020; Chinchilla 2022): loss falls predictably with more compute, data and parameters. Test-time compute: OpenAI's o1 (Sept 2024) improved with more time spent thinking; current Claude models use adaptive thinking guided by an effort setting.

{
  "model": "claude-opus-5-5",
  "max_tokens": 16000,
  "thinking": { "type": "adaptive" },
  "output_config": { "effort": "high" },
  "messages": [{ "role": "user", "content": "Plan a database migration." }]
}

New architectures: state space models such as Mamba (2023) process sequences in linear time; hybrids such as AI21's Jamba mix them with attention; diffusion language models refine many tokens in parallel.

L5Demo, research, product or marketing?

AI news mixes four very different kinds of claim. Learn to tell them apart before relaying anything.

TypeSignals
productionA public model ID or product, a price page, docs, a changelog. You can call it yourself today. Generally available, not preview or waitlist.
researchA paper or preprint with method, data and limits. Maybe code or weights. No price, no service guarantee. Results come from one fixed setup.
demoA video, keynote or blog with chosen examples. "Rolling out soon", waitlists, trusted testers. No API, no price, no failure rates.
claimSuperlatives, the vendor's own benchmark with no outside re-run, new benchmark names, "up to N× faster" without a baseline.

Five quick checks

  1. Can I call it with a public ID right now?
  2. Has anyone outside the company re-run the number?
  3. Is there a date and a version?
  4. Does it say "preview", "trusted access" or "coming weeks"?
  5. Do sources disagree? Then treat it as unverified.

QA perspective

  • Before testing anything a vendor announced, confirm it is actually available in your account and region.
  • Re-run vendor benchmarks on your own tasks before trusting them.
  • Record the model ID and date with every result, because names stay the same while models change.
